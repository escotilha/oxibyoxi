# oxi dogfood roadmap

The queue the `oxi-adapter-self` dogfood loop picks from. Each item is a bold line shaped `**T{tier}-{N} · {title}**` followed by an italic subtitle — the planner reads this format.

Keep it tight — 10-15 open items at a time. Items ship as individual PRs.

Conventions:

- **Tier 0** — blockers, safety/security, installer bugs. Dispatch first.
- **Tier 1** — user-visible polish, runbooks, CLI ergonomics.
- **Tier 2** — internal cleanup, test coverage, refactors.

The roadmap is auto-pruned weekly by `.github/workflows/roadmap-prune.yml` — items get removed when there's a substantive merged commit on `main` naming the T-id.

---

Every item below has a PR open and auto-merge enabled. The weekly auto-prune workflow removes each line once its T-id appears in a substantive merged commit on `main`.

## Tier 0 — operational pain from 2026-04-25 dogfood

**T0-104 · file-overlap dispatch gate**
_before each `dispatch_one()` claims a planned task, query `gh pr list --json number,headRefName,files` for currently-open PRs originating from the engine. If the planned task's expected file scope overlaps with any open PR's `files`, defer the dispatch (re-mark as planned with a `last_deferred_at` timestamp; pick a different non-overlapping task). The "expected file scope" is read from the existing `files_touched` field on `task` (per Contably's v4.1 gate pattern). Acceptance: dispatching 5 codex-series tasks (T2-31..T2-37) in parallel produces zero merge conflicts on the resulting PRs; each task waits its turn. Caused by 2026-04-25 cascade where 5 codex-series PRs all opened cleanly then conflicted at merge-time, requiring manual close+reset for 4 of them._

**T0-108 · split heavy ML deps into an optional `[dedup]` extra**
_a fresh `pip install --pre oxi-core==0.1.0b2` from TestPyPI pulls in torch 2.11.0, transformers 5.6.2, sentence-transformers 5.4.1, scikit-learn 1.8.0, scipy 1.17.1, numpy 2.4.4 — collectively ~2GB of download and several minutes of install time on a typical connection. Verified during 2026-04-26 TestPyPI smoke test. These deps are required by the auto-improve subsystem's three-layer dedup (T1-B7, cosine similarity over front+task history), but they are NOT required by the core engine — `oxi v3 saturate`, `oxi v3 tick`, dispatch, critic, and the wizard work without any of them. Strangers who just want to run the engine pay the ML-deps tax for a feature they may never enable. Move the heavy deps behind an `[dedup]` (or `[auto-improve]`) optional dependency in `oxi-core/pyproject.toml`; gate the import in `dedup.py` with a try/except that surfaces a clear `pip install oxi-core[dedup]` error when the feature is invoked without the extras. Acceptance: a fresh `pip install --pre oxi-core==0.1.0bN` (no extras) downloads <50MB and completes in under 30 seconds; `oxi v3 saturate` runs without errors as long as auto-improve is disabled in `routing.yaml`; running auto-improve without the extras emits a single actionable error pointing at the install command. Caught during the b2 TestPyPI smoke; not a release blocker for b2 (the install works, it's just slow), file as Tier 0 because the onboarding cost is high enough to deter trial users._

**T0-109 · ledger event for wall-clock dispatch timeouts**
_`dispatch_invoke.py` correctly classifies `TimeoutError` as `TIMEOUT` (line 424) but `dispatch.py` never writes a specific ledger event distinguishing wall-clock timeouts from other abandonments. Tasks transition to `abandoned` with a generic reason, losing the operator-debugging signal that the timeout was budget-driven vs. heartbeat-stale vs. user-canceled. Add `EVENT_DISPATCH_WALL_CLOCK_TIMEOUT = "dispatch_wall_clock_timeout"` to `ledger_events.py` and a `dispatch.ledger.append()` call in the timeout-handling path before `_transition_to_abandoned`. Event payload should include `wall_clock_seconds`, `wall_clock_timeout_s` from the invocation, and the worker's last `assistant` event content (truncated to 500 chars) so reviewers can see what the worker was doing when the cap hit. Acceptance: tasks that go past the wall-clock budget emit one `dispatch_wall_clock_timeout` ledger row distinct from generic abandonment; existing tests that grep for "abandoned" still pass; new test asserts the event fires on a forced timeout. Scope: ~15 LOC + 1 test. Not blocked._

**T0-110 · narrow transaction scope for dispatch result write**
_`dispatch.py` updates the task row atomically (`with conn:` line ~402) but only AFTER `dispatch_invoke.invoke()` finishes parsing the entire event stream. A SIGKILL or process crash between `proc.wait()` returning and the DB statement landing leaves the task row stuck in `dispatched` until heartbeat reaps it (T0-105 grace period defaults to 30 minutes). The reaper exists, but narrowing the orphan window improves perceived engine responsiveness — especially under concurrency 5+ where one zombie blocks one of N concurrent slots. Refactor: move the result-event parsing into a single transactional block so DB updates land as soon as the result event is available, not after all subsequent events drain. Be careful not to widen the transaction so much that holding a SQLite lock starves other workers. Acceptance: a forced SIGKILL of a worker after `proc.wait()` returns but before the DB statement runs is now a no-op (the task is already updated) instead of orphaning the slot for 30 minutes; existing dispatch tests still pass. Scope: ~25 LOC. Not blocked._

**T0-111 · scrub all ANTHROPIC_* env vars except API_KEY before subprocess spawn**
_`dispatch_invoke.build_env()` starts from `_BASE_ENV_WHITELIST` (line 80) and explicitly injects `ANTHROPIC_API_KEY` (line 209), but any other `ANTHROPIC_*` vars in the parent process (e.g. `ANTHROPIC_MODEL`, `ANTHROPIC_BASE_URL`, future SDK config vars) leak through the union on line 204. Risk is moderate: a stale `ANTHROPIC_BASE_URL` in the operator's shell could silently redirect dispatched workers to the wrong endpoint, including a malicious one set by a prior compromise. Add a post-build filter that strips all keys matching `re.match(r"^ANTHROPIC_", k)` from the assembled env, then re-injects only the explicit `ANTHROPIC_API_KEY` we want. Same treatment for any `OPENROUTER_*`, `XAI_*` keys for LiteLLM gateway hygiene. Acceptance: a unit test that sets `ANTHROPIC_BASE_URL=http://evil.example.com` in the parent env confirms the spawned subprocess does NOT see that var; only `ANTHROPIC_API_KEY` (the injected one) is present. Scope: ~15 LOC + 1 test. Not blocked. Filed as T0 because env-leak attack surfaces deserve fast attention even when current risk is low._

**T1-26 · improve dispatch spawn-failure error messages**
_when `asyncio.create_subprocess_exec()` fails (dispatch_invoke.py:346, e.g. `claude` binary not on PATH, cwd doesn't exist, env too large for `execve`), the `OSError`/`FileNotFoundError` propagates to `dispatch_one()`'s generic `except` and the task transitions to `failed` with a stack-trace log. Operators see "FileNotFoundError: [Errno 2] No such file or directory: 'claude'" with no context about what `cwd`, what `binary` path, or what env was attempted. Wrap the `create_subprocess_exec` call in a try/except that catches `OSError | FileNotFoundError`, logs `cwd={cwd}, binary={argv[0]}, errno={e.errno}, strerror={e.strerror}, argv_first_500={shlex.join(argv)[:500]}`, then re-raises wrapped in a new `DispatchSpawnError` with the same structured fields. The classifier in `dispatch.py` should treat `DispatchSpawnError` as `RETRYABLE_TRANSIENT` if errno is `EAGAIN`/`ENOMEM`, `FAILED` otherwise. Acceptance: a fake adapter pointing `claude_binary` at `/nonexistent/claude` produces a log line with full diagnostic context, not a bare `FileNotFoundError`. Scope: ~25 LOC + 1 test. Not blocked._

**T1-27 · heartbeat reaper logs which task IDs it abandoned**
_`heartbeat.reap()` writes a single `ReapReport(considered, abandoned, protected_by_pr, skipped_fresh)` summary but never logs which specific task IDs it transitioned to abandoned. Operators debugging "why did my queue lose progress?" have no audit trail without going to the ledger directly. Add a `logger.info(f"heartbeat: abandoned {task.identifier} (last_progress_at={ts}, age_seconds={age})")` per reaped task in the loop. Add an `abandoned_ids: list[str]` field to `ReapReport` for programmatic access. Existing tests that assert on `report.abandoned == N` still pass since that count is preserved. Acceptance: a 3-task reap emits 3 INFO-level log lines with task identifiers; the report dataclass has the new field populated. Scope: ~20 LOC + 1 test update. Not blocked._

**T2-53 · auto_merge.py loads full task rows when only ID + PR number needed**
_`auto_merge._load_candidates()` (auto_merge.py:80) issues `SELECT * FROM task WHERE status = 'dispatched'` and filters in Python. Each row pulls the full `dispatch_output` column, which can be tens of KB of JSONL per task. Under concurrency 5+ with a deep dispatched queue (50+ rows), this wastes SQLite I/O and Python memory on data the function never reads. Change the query to `SELECT id, identifier, pr_number, dispatch_started_at, attempt_count FROM task WHERE status = 'dispatched'` (only the columns actually consumed by the filter + update). Add a unit test that asserts the SELECT in this code path lists explicit columns (regression test against future drift back to `SELECT *`). Acceptance: SQLite query plan for `auto_merge` shows reduced row width; benchmark on a synthetic 100-task dispatched queue shows >50% memory reduction. Scope: ~15 LOC + 1 test. Not blocked._

**T2-54 · `oxi v3 tick` swallows ingest failures silently across iterations**
_`cmd_tick` calls `ingest_roadmap.ingest()` per iteration (cli.py:438). If ingest fails on iteration 2 (e.g. `docs/roadmap.md` was renamed mid-tick or has a parse error after a manual edit), the exception propagates up but the operator only sees the half-finished tick summary and may not realize ingest failed silently. Wrap the ingest call in a per-iteration try/except: on failure, log `WARNING tick {iteration}/{total}: ingest failed; continuing with stale roadmap` with `exc_info=True`, increment a counter on `ReapReport`-equivalent for the tick run, do NOT re-raise (continuing with stale data is usually safer than crashing mid-tick). Print a yellow summary line at the end if any ingest failures occurred: "⚠ ingest failed N times; last roadmap state in DB is stale". Acceptance: a missing `docs/roadmap.md` mid-tick produces one warning per iteration but does NOT crash the tick; the final summary surfaces the failure count. Scope: ~15 LOC + 1 test. Not blocked._

**T2-55 · troubleshooting runbook is a stub**
_`docs/runbooks/troubleshoot.md` (if it exists; check) is the natural first port for operators when `oxi status` shows unexpected state. Currently a stub. Build it from real incidents observed during 2026-04-25 + 2026-04-26 dogfood: (1) "zero planned tasks after `oxi v3 tick`" — diagnostic flow: `oxi v3 plan --dry-run`, check `roadmap_location()`, check `repo_root` is correct; (2) "dispatch failing with `CalledProcessError` or `FileNotFoundError`" — link T1-26's diagnostic output once it lands; (3) "heartbeat isn't reaping stale dispatches" — explain the grace period, link T0-105 once landed; (4) "critic backend not configured" — clarify the critic-skip default and the `--real-claude` flag's role; (5) "multiple adapters installed" — the `OXI_ADAPTER` pin pattern from `AGENTS.md`; (6) "`pip install` fails with `Could not find a version`" — Python 3.9 cliff. Each section: 1-paragraph problem statement, 3-step diagnostic, 1-step fix. Total ~300 lines of markdown. Acceptance: a fresh operator with each of those 6 problems can resolve via the runbook without filing a GitHub issue. Scope: ~300 lines of markdown, no code. Not blocked._

**T0-112 · `oxi init` and `oxi status` should detect missing ANTHROPIC_API_KEY**
_during 2026-04-26 dogfood, `oxi v3 saturate` started cleanly, dispatched 5 workers, and every worker exited within 1 second with `Not logged in · Please run /login` — because `ANTHROPIC_API_KEY` was unset in the environment. The wizard never asked, `oxi status` never warned, the only signal was 5 consecutive `dispatch_failed` events with `cost_usd=0.0, wall_clock_seconds<1`. Add a credential check to (a) `oxi init` final review screen — print "⚠ ANTHROPIC_API_KEY not set; workers will fail authentication. Get a key at https://console.anthropic.com/ and export it before running `oxi v3 saturate`" — non-blocking warning, scaffold proceeds; (b) `oxi status` — show a status line "auth: ANTHROPIC_API_KEY ✓ set" or "auth: ANTHROPIC_API_KEY ✗ missing"; (c) `oxi v3 saturate` startup — refuse to start if neither `ANTHROPIC_API_KEY` is set nor `~/.config/anthropic/api_key` exists, with the same actionable error pointing at console.anthropic.com. Acceptance: a fresh install with no API key reaches the warning at oxi init review, not after wasted dispatches. Scope: ~30 LOC + 2 tests. Filed as T0 because the failure mode burns 5 worker dispatches and triggers engine_unhealthy unnecessarily — pure UX waste with no diagnostic signal. Caught when saturate stopped after 4 iterations on commit f37ca53._

**T1-28 · dispatch_failed event payload should include the worker's last assistant message**
_when a worker exits with error (auth failure, model error, etc.), the `dispatch_failed` ledger event records `session_id`, `exit_code`, `cost_usd`, `wall_clock_seconds`, `classification` — but NOT the actual error string from the worker's last `assistant` event. Operators have to reconstruct the failure by re-running the exact subprocess invocation manually. Add a `last_message: str` field to the dispatch_failed payload, populated from the worker's last `assistant` event content (truncated to 500 chars) before the result event. For T0-112's auth-failure case, this would have shown "Not logged in · Please run /login" directly in `oxi v3 status` recent events. Acceptance: a forced auth failure shows the auth error string in the ledger event payload; SQL query `SELECT json_extract(payload, '$.last_message') FROM event WHERE kind='dispatch_failed'` returns the worker's exit reason. Scope: ~15 LOC. Not blocked. (Overlaps with T0-109 — combine implementation if both land in same PR.)_

**T2-56 · engine_unhealthy event should include sample of failed task IDs and their reasons**
_when the consecutive-failure threshold trips, the `engine_unhealthy` event records `consecutive_failures: 5, reason: "failed"` — useless, because "failed" is the same generic classification on every failed dispatch. Operators see the engine paused and have to hand-query `task` and `event` tables to figure out what happened. Augment the event payload: include `failed_task_ids: list[str]` (the 5 task identifiers that triggered the gate) and `last_failure_reasons: list[str]` (the per-task last_message from T1-28, or fallback to classification if T1-28 hasn't landed). Operators reading recent events see the trip cause inline. Acceptance: when engine pauses after 5 consecutive auth failures, the `engine_unhealthy` event payload shows `["T0-104", "T0-107", "T0-106", "T0-105", "T0-108"]` and 5 "Not logged in" strings. Scope: ~25 LOC. Soft-depends on T1-28 for the per-task message; without it, falls back to classification only._

**T0-106 · `0.1.0b1` PyPI wheel cannot seed the roadmap (release blocker)**
_a stranger running the README's install snippet (`pip install --pre oxi-core` → `oxi init` → `oxi v3 tick --times 1`) cannot get a single task into the planned queue. Root cause is the intersection of two gaps: (a) `oxi v3 saturate` — the only CLI surface that calls `ingest_roadmap` + `seed_from_roadmap` — is not in the published `0.1.0b1` wheel (it postdates the release; `from oxi_core.cli import cmd_saturate` raises `ImportError` against the installed wheel); (b) `oxi v3 tick` does not ingest (filed as T2-48). Net effect: a fresh install with valid `docs/roadmap.md` and 39 parseable items via `oxi v3 plan --dry-run` shows `task counts by status: (no tasks)` forever. No workaround except `pip install -e ./oxi-core` against a source checkout, which strangers will not have. Caught during 2026-04-26 dogfood. Fix path: cut a `0.1.0b2` PyPI release that includes the post-b1 saturate work AND T2-48 (tick ingests at head of iteration). Either alone is sufficient to unblock; shipping both is cheap and prevents this class of bug recurring as the supervisor pattern evolves. Acceptance: a fresh `pip install --pre oxi-core` followed by the README's onboarding sequence ends with a non-empty `oxi status` task count without requiring `saturate`. CI gate: a smoke test that pip-installs the just-built wheel into a clean tempdir, runs the onboarding sequence end-to-end, and asserts `task counts > 0` — would have caught this before b1 shipped._

**T0-105 · heartbeat reaper for zombie dispatches**
_currently if a worker dies without writing back (SIGKILL, parent supervisor crash, claude-code timeout-bug #45717), the task row stays `dispatched` forever and blocks the engine's view of in-flight count. Add a heartbeat: `dispatch_one()` writes `last_progress_at` to the task row at start; a new `reaper.py` runs at the head of every tick, finds tasks with `status='dispatched' AND last_progress_at < now() - 30min` AND no live worker process matching the session_id, and resets them to `planned`. Includes a process-existence probe (psutil or `kill -0`) — never reset a task whose worker is genuinely still running. Acceptance: stale `dispatched` rows from a killed supervisor don't accumulate; queue stays accurate. 8 such zombies appeared in the 2026-04-25 PM dogfood, blocking the engine's concurrency view._

_today the entry-point auto-discovery can't load `SelfAdapter(repo_root=...)` because the discovered class needs no-arg construction. ## Tier 2 — operator polish from 2026-04-25 pain

**T2-43 · CPU-aware concurrency probe**
_RAM probe (`compute_probe.recommend_ram_concurrency()`) recommends N workers based on free RAM, but doesn't consider CPU. On 2026-04-25, the probe recommended 7 workers on a Mac mini that was already at load avg 13 from non-oxi processes (Warp, openclaw-node, etc.) — adding 7 more workers pushed load to 36+. Extend the probe to also read load avg / CPU count and compute `cpu_envelope = max(1, cpu_count - load_avg_5min)`. Final recommendation: `min(ram_envelope, cpu_envelope, plan_tier_envelope, ceiling)`. Acceptance: on a busy host, probe recommends fewer workers than RAM alone would suggest; never spawns past load capacity._

**T2-44 · auto-merge enforcement on critic pass**
_today auto-merge requires both (a) the engine arming `gh pr merge --auto` and (b) GitHub's auto-merge feature being enabled at repo level. Several PRs today required manual `gh pr merge` because step (a) was missed during PR creation. Make critic.py the single point of arming: when the critic returns APPROVE, the same code path that records the verdict also calls `gh pr merge --auto --squash --delete-branch` via `GhCliClient`. Idempotent — already-armed PRs no-op cleanly. Acceptance: every critic-approved PR has auto-merge armed without operator intervention; verified by querying `pull_requests.auto_merge` field on next tick._

**T2-45 · `oxi v3 saturate` continuous-dispatch CLI command**
_today the supervisor pattern is a bash script (`~/.oxi-supervisor.sh`) running in tmux. Make it a first-class oxi subcommand: `oxi v3 saturate --concurrency N --max-cost-per-day USD`. Loops continuously: each iteration calls ingest → auto_observe → seed → dispatch_loop. Tracks daily cost and exits cleanly when the hard cap is hit (logs a `daily_budget_reached` event). Daemon-ready: writes a PID file at `adapter.paths().repo_root + ".oxi/saturate.pid"`; refuses to start if a live PID exists; signal-safe shutdown on SIGTERM (waits for in-flight workers, doesn't kill them). Acceptance: replaces the bash supervisor entirely; can be wrapped by launchd/systemd/tmux with no shim. 10 hours of validated continuous-dispatch on 2026-04-25 makes this the next abstraction to formalize._

**T2-46 · wizard learns about the AgenticAdapter choice**
_today's `oxi init` step 6 asks "Claude plan tier (e.g. standard, max_5x, max_20x)" — accurate while the agentic worker is hardcoded to `claude -p`, but once T2-30 lands the operator can pick a different agentic adapter (Claude, Codex, future Aider). Replace the single plan-tier prompt with a two-stage step: (a) "Agentic worker (claude/codex)" defaulting to `claude`; (b) plan tier prompt only asked if `claude` is selected (Codex has its own pricing model surfaced via `codex_rates.yaml`). Wizard writes the choice into the scaffolded adapter's `agentic_adapter_name() -> str` method, which `dispatch.py` reads via the T2-30 protocol. Doc clarifications from commit f34797c (agentic vs non-agentic split in README + install runbook) become the reference text for the new prompt's help line. Acceptance: a fresh `oxi init` run with `codex` selected scaffolds an adapter that reports `adapter=codex` in `oxi status`; the existing `claude` path stays the default and reads identically to today's wizard. Depends on T2-30, T2-31, T2-34 (the agentic adapter protocol + a working second adapter must exist before the wizard offers the choice)._

**T2-47 · wizard: editable destination + repo-root sanity check**
_the review screen already prints `Destination: {path}` (`wizard._render_review` line 450) but offers no way to change it without aborting the whole wizard. Two compounding paper cuts: (a) destination is `Path.cwd() / f"oxi-adapter-{slug}"`, so running `oxi init` from one directory above your project checkout silently scaffolds the adapter outside the repo (caught during 2026-04-26 dogfood when `oxi init` from `~/code/` produced `~/code/oxi-adapter-oxibyoxy/` while the user assumed it would land inside `~/code/oxibyoxi/`); (b) typos in the slug (`oxibyoxy` vs `oxibyoxi`) bake into the package name on disk and are tedious to fix after the fact. Add a confirmation prompt on the review screen: "Destination [{default}]:" — empty input keeps the default, otherwise the operator types a new absolute path. Validate the path is absolute and writable. Also: if the entered destination is not inside `answers.repo_root` (the value the operator gave for "repo root"), print a single yellow warning line — does not block, just surfaces the mismatch before files are written. Acceptance: pressing Enter on the new prompt preserves today's behavior bit-for-bit (test snapshot); typing a new path writes there instead; outside-repo-root scaffolds emit one warning line. Not urgent — operators who notice immediately can rm -rf and re-run, which is what the 2026-04-26 dogfood did._

**T2-48 · `oxi v3 tick` should run a roadmap-ingest pass before dispatch**
_today only `oxi v3 saturate` calls `ingest_roadmap` + `seed_from_roadmap`; a single tick (`oxi v3 tick --times 1` or `--real-claude`) skips ingest entirely and dispatches whatever's already seeded. The README's smoke-test step is `oxi v3 tick --times 1`, which succeeds cleanly with `task counts by status: (no tasks)` on a fresh install — no signal to the operator that ingest hasn't run. Caught during 2026-04-26 dogfood: fresh install, correct adapter, correct roadmap_location, valid roadmap.md — but `oxi status` showed zero tasks because no command in the README's onboarding sequence ingests. Two acceptance paths to consider: (a) tick gains an ingest pass at the head of every iteration, gated by `--no-ingest` for the rare case the operator wants to skip; (b) tick prints a one-line warning when the planned-task count is zero AND the roadmap file exists with parseable items. (a) is the right shape — saturate already does it that way and the duplication is the actual bug. Acceptance: a fresh install with valid `docs/roadmap.md` populates the planned queue after one `oxi v3 tick --times 1` run; the README's onboarding smoke test produces a non-empty `oxi status` without needing `saturate` to run first._

**T2-49 · `oxi init` stats the roadmap path before scaffolding**
_the wizard accepts `roadmap_location` as a free-text string (default `roadmap.md`) and never checks whether `repo_root + roadmap_location` actually exists. Engine repos commonly keep their roadmap at `docs/roadmap.md`, not the wizard's default — caught during 2026-04-26 dogfood where the wizard accepted `roadmap.md` against an `oxibyoxi` checkout whose roadmap is at `docs/roadmap.md`, producing a fresh install with zero ingestable tasks. Add a stat check inside `_valid_roadmap_location` (or a separate post-prompt warning, since validators today are pure): if the resolved path doesn't exist, print "⚠️ no file at {full_path} — continue anyway? [y/N]". On `n`, re-prompt the location. On `y`, scaffold as today. Acceptance: a wizard run against a repo with a roadmap at `docs/roadmap.md` and the operator accepting the `roadmap.md` default gets a clear warning + the chance to fix; the validator stays pure (warning logic in collect_answers, not the validator). Cheap fix that closes one of the two top onboarding paper cuts (the other being T2-48)._

**T2-50 · drop `--dry-run` flag from `oxi v3 plan` (single-mode subcommand)**
_`oxi v3 plan` is parse-only and read-only — `cmd_plan` (cli.py:686) explicitly documents "Does NOT touch the DB" and `--dry-run` is `required=True` (cli.py:926). The flag is mandatory and tautological: there is no non-dry-run mode to disambiguate from. Operators run `oxi v3 plan` and get `error: the following arguments are required: --dry-run`, then re-type with the flag — pure friction. Two acceptable shapes: (a) drop `--dry-run` entirely and rely on the help text + command docstring to say "this is read-only" (cleanest); (b) make `--dry-run` the default behavior and add `--seed` as the future opt-in for the actual DB-touching path, when that path is built. Recommend (a) since (b) is speculation about a feature that doesn't exist. Acceptance: `oxi v3 plan` runs with no flags and produces today's `--dry-run` output; remove `--dry-run` from the CLI table in cli.py docstring and the install runbook. Caught during 2026-04-26 dogfood when the operator was diagnosing a zero-tasks install._

**T2-51 · release.yml: skip-existing on TestPyPI uploads (idempotent re-runs)**
_today's `release.yml` workflow uses `pypa/gh-action-pypi-publish@release/v1` with default `skip-existing: false`. When an operator re-triggers the testpypi target after a successful previous publish, the action errors out with `400 File already exists` and the run is marked failed — even though the desired end state (the wheel is on TestPyPI) is already true. Caught during 2026-04-26 b2 cut: a second testpypi run for verification purposes failed solely because the wheel from the first run was already published. Fix: in `.github/workflows/release.yml`, add `with: skip-existing: true` to the `publish_testpypi` job's `pypa/gh-action-pypi-publish` step. Leave the `publish_pypi` job's setting unchanged (skip-existing: false) — accidentally re-publishing to real PyPI should fail loudly because version-already-exists is real signal there, not noise. Acceptance: re-running the testpypi target on a wheel that already exists on TestPyPI succeeds with a "skipping existing" log line; re-running pypi target on an existing version still fails. Trivial fix — single line + an explanatory comment. Caught during 2026-04-26 b2 release._

**T2-52 · release.yml: pre-flight check that pyproject version is unpublished on target index**
_today's `release.yml` workflow happily runs build + smoke (~2 minutes of CI minutes) before the publish step finds out the version already exists on the target index. Wasteful when the operator forgot to bump pyproject.toml or accidentally re-ran an already-published version. Add a new job at the head of the workflow (before `build`): `preflight` — reads version from `pyproject.toml`, queries `https://{target_index}/pypi/oxi-core/json` for `releases.{version}`, fails fast if the version exists on the target. For TestPyPI: skip the check or make it warn-only since T2-51 is making testpypi re-runs a non-error path anyway. For real PyPI: hard-fail with a message like `oxi-core 0.1.0bN is already on PyPI; bump pyproject.toml/version before re-running`. Acceptance: workflow targeted at pypi for an already-published version fails in <10 seconds (preflight job alone) instead of after ~2 minutes of build+smoke; targeted at testpypi for an existing version either passes (warn-only) or matches T2-51's skip-existing behavior. Depends on T2-51 (decide testpypi semantics together). Caught during 2026-04-26 b2 release while diagnosing a re-run failure._
